# Rules: vlsit-rtl-hierarchy-diagram

Authority: this file is the highest-priority source for the skill. Every rule below is mandatory. `SKILL.md` defines the workflow that satisfies these rules; `references/` holds supporting information and examples that rank below this file. If any other file conflicts with a rule here, follow the rule and report the conflict.

Keywords: MUST and MUST NOT admit no waiver. SHOULD is followed by default and may be deviated from only with a stated reason in the final report.

## A. General

- RHD-001 (MUST): Write all skill output (diagram labels, notes, reports, script messages, code comments) in precise scientific and engineering English, and distinguish RTL-proven facts from interpretation. Bilingual content is allowed only in README files and documents designated as user guidelines.
- RHD-002 (MUST NOT): Modify RTL source files. The skill only analyzes RTL.

## B. Input

- RHD-010 (MUST): Before locating or reading any RTL, require an explicit path to the RTL source directory for the current request. If missing, ask "Please provide the path to the RTL directory you want analyzed." and wait.
- RHD-011 (MUST NOT): Infer the RTL directory from the working directory, repository root, skill directory, output path, or an unrelated earlier task. If the path is invalid or ambiguous between a repository root and the RTL source directory, ask for clarification.
- RHD-012 (MUST): The user chooses the diagram level N, a positive integer: level 1 draws the TOP module as a frame containing its children, level 2 adds the next level, and so on. The TOP module alone is never drawn as a separate page (RHD-041); if the user gives 0, explain this and use level 1. If the request does not state a level (or `all` for the full depth), ask for it in the same message as the RTL path (RHD-010) and wait. The skill MUST NOT assume a default level.
- RHD-013 (MUST): Analysis and drawing are limited to levels 1 through N (the top module itself is level 0 and is analyzed as the parent frame). If N exceeds the actual hierarchy depth, use the deepest existing level and tell the user. A block at level N that instantiates submodules (or has own logic, RHD-084) is drawn as a normal block marked `(not expanded)` in its function note, and the report lists its direct child module names without analyzing them further. Interfaces of drawn blocks remain complete (RHD-058).

## C. Symbol library

- RHD-020 (MUST): Use only `assets/VLSIT_DRAWIO_LIB_V1.drawio.xml` as the source of every visible block, frame, logic symbol, IO pad symbol, connector, and text annotation. The only other shapes are the native table cells permitted by RHD-023. Read `references/library_usage.md` before generation.
- RHD-021 (MUST): Clone complete template cell structures, remap identifiers and internal references, and keep template provenance on each cell as specified in `references/library_usage.md`. Use entry 32 for module blocks and frames, entry 0 for standalone text and labels, entry 1 (straight arrow with an explicit waypoint polyline) for every connector, and entry 5 for IO pad symbols. Entry 27 is not used because its orthogonal style does not keep explicit waypoints.
- RHD-022 (MUST): Preserve template shape definitions, gate operations, arrowheads, and group topology. Only labels, placement, dimensions, and permitted presentation properties may change. Permitted properties are those in `EDITABLE` of `scripts/library_symbols.py`, which includes the line-jump properties `jumpStyle` and `jumpSize` used by RHD-057.
- RHD-023 (MUST NOT): Import other libraries, use unrelated built-in symbols, insert images, or invent substitute shapes. The only exception is the native draw.io table (shapes `table`, `tableRow`, and `partialRectangle` cells) used for the two description tables of RHD-046 and RHD-089, as authorized by the user; every table cell carries the attribute `vlsit_native_table="1"` instead of library provenance, uses 18 pt black text on a white or transparent fill with black borders, and is not used for any other purpose. If a required symbol is absent, ask for a library extension or an agreed representation built from existing templates.
- RHD-024 (MUST): Replace library placeholders with source-grounded content. Use logic symbols only when the requested detail and the RTL justify them.
- RHD-025 (MUST): If the bundled asset is missing, unreadable, or invalid, stop generation and ask for the correct library. Do not substitute a local-machine file or regenerate a copy from memory.

## D. Analysis

- RHD-030 (MUST): Locate RTL files and project context (file lists, build scripts, constraints, configuration). Respect user-specified source and output paths.
- RHD-031 (MUST): Identify the top module from the instruction or project configuration. If several candidates remain, state them and the assumption used.
- RHD-032 (MUST): Trace instantiations recursively down to the selected level N (RHD-012, RHD-013), recording instance name, module name, source file, depth, parent, parameters, and generate scope. Packages and interfaces are source context, not module blocks, unless instantiated as modules.
- RHD-033 (MUST): Trace port connections through parent nets and assignments, including sibling modules connected via the parent. Distinguish actual RTL connections from functional interpretation.
- RHD-034 (MUST): Describe each relevant module from its RTL (state, datapath, control, port behavior), not from names or comments alone. State an instance-specific role only when connections and surrounding RTL support it; otherwise give the module-level role and mark the instance role unclear.
- RHD-035 (MUST): Identify standard and internal interfaces (APB, AXI channels, valid/ready, request/acknowledge, FIFO push/pop, interrupts, others) from actual port mapping and handshake behavior, confirmed by several signals and behavior rather than by a name. Record direction, endpoints, and key signals present and connected.
- RHD-036 (MUST): Account for generate blocks and parameters when the active hierarchy is clear. When several configurations are possible, label conditional branches and explain the uncertainty.
- RHD-037 (MUST NOT): Invent modules, instances, connections, protocol compliance, or behavior. Mark unresolved or external modules explicitly.

## D2. Staged flow, signal analysis, and analysis report

- RHD-070 (MUST): Execute the work in this order and finish each stage before the next: (1) hierarchy analysis, (2) block/module function analysis, (3) signal and interface analysis, (4) signal grouping, (5) analysis report in one Markdown file, (6) diagram drawing. The diagram MUST NOT be started before the report (stage 5) is written.
- RHD-071 (MUST): Stage 2 gives each module a main function derived from its RTL (RHD-034), per instance its role in the design when supported by wiring, and, for modules with own logic, the functional-group analysis of RHD-080 to RHD-083.
- RHD-072 (MUST): Stage 3 analyzes every signal connected between blocks (parent-to-child and sibling-through-parent) and records for each: name(s) at both endpoints, direction, width, source and destination instance, functional meaning, clock domain when evident, and signal type: level or pulse (single-cycle or multi-cycle), data, address, control, status, interrupt, clock, or reset. Level versus pulse MUST be justified by RTL behavior (for example a register that self-clears, or a one-cycle assignment), not by the name. If the type cannot be determined from RTL, mark it "unclear" with the reason.
- RHD-073 (MUST): Stage 3 classifies each interface into exactly one category: (a) standard protocol (name and version, for example APB, AXI4, AXI4-Stream, Wishbone, AHB), (b) handshake interface (valid/ready, request/acknowledge, FIFO push/pop, enable/done), or (c) custom interface. A standard-protocol label requires the protocol's mandatory signals and behavior to be present (RHD-035); partial matches are reported as "protocol-like" with the missing signals listed. Custom interfaces are described signal by signal.
- RHD-074 (MUST): Stage 4 partitions signals into named interfaces. An interface is a set of functionally related signals that together carry one kind of transaction between two blocks, like the signals of a bus protocol (requests, responses, data, strobes, status). All signals of such a set belong to ONE interface even when they are named differently or travel in both directions (for example a host bus formed by address-latch, read, write, chip-select and bidirectional data signals, or a request signals plus the returned data). Separate interfaces are formed only for signals that serve a different function or a different pair of blocks, and for dedicated off-chip line interfaces, which are always drawn separately per pin (RHD-100). Remaining signals are grouped by function (clock/reset, status, configuration, data). Every inter-block signal belongs to exactly one interface; signals that cannot be grouped are listed under an explicit `Ungrouped` group.
- RHD-075 (MUST): Stage 5 writes all hierarchy, module-function, signal, interface, and group analysis into a single Markdown file named `rtl_analysis.md` in the same folder as the diagram unless the user specifies another path. Do not silently overwrite an existing report; use a numbered name or ask. Structure follows `references/analysis_template.md`.
- RHD-076 (MUST): `rtl_analysis.md` contains at least: scope and evidence (files inspected, top, configuration assumptions, evidence level), hierarchy tree with instance inventory, module function table, signal table per interface, interface classification table (standard / handshake / custom, with evidence), signal-group table, and conditional or unresolved items. Facts proven by RTL and interpretation are labeled separately (RHD-001).
- RHD-077 (MUST): The diagram is derived from `rtl_analysis.md`: every block, interface connector, and group label in the diagram appears in the report, and the report is updated first when analysis changes.
- RHD-078 (MUST): Interface categories and the catalog in `references/interface_groups.md` are examples, not a closed list. When analysis finds a signal group that matches no catalog entry (for example a debug/trace, test/scan, power-management, DMA request, calibration, or vendor-specific interface), the skill MUST (1) still analyze and draw it under a provisional descriptive name marked `(proposed group)`, (2) list it in `rtl_analysis.md` section 6 with its signals and evidence, and (3) at the end of the run ask the user whether to add it to the catalog and, if the drawing or analysis rules need to change, to update `rule.md`. The catalog, `SKILL.md`, and `rule.md` are updated only after the user approves (RHD-094); the answer and any resulting change are logged in `references/improvement_log.md`. The skill MUST NOT wait for the answer to deliver the diagram.
- RHD-080 (MUST): A module has own logic when it contains behavioral or dataflow code beyond trivial wiring: `assign` with operators or conditionals, `always`, `always_ff`, `always_comb`, `always_latch`, functions or tasks used by that logic, and logic inside `generate` blocks. Plain port-to-net connections, constant ties, and simple renames are not own logic. `initial` blocks and simulation-only code are excluded from grouping and noted in the report. A module may have both child instances and own logic.
- RHD-081 (MUST): For every module within the selected level (RHD-013) that has own logic, partition that logic into functional groups by function (for example register file, FSM, datapath, counter, FIFO pointer logic, synchronizer, interrupt logic, output mux), not by construct type or source order. Every own-logic statement belongs to exactly one group, traceable by file and line range. At most 10 functional groups per module (the limit applies to the module's own logic only, not to child instances). When more than 10 candidate groups exist, merge by functional affinity until 10 or fewer remain, and state each merge and its rationale in the report. Residual trivial logic goes into a single `Glue logic` group. The limit MUST NOT be exceeded.
- RHD-082 (MUST): A module whose own logic forms fewer than two functional groups is not expanded; its function is described in the module function table (RHD-071). A module with two or more groups is expanded into functional-group blocks.
- RHD-083 (MUST): `rtl_analysis.md` records for each module its functional groups in a table: group name, function, constructs and line ranges, state elements, signals driven, inputs consumed, and outputs to other groups or module ports. The signals between functional groups and between groups and the module ports are analyzed, classified, and grouped under RHD-072 to RHD-074, with level/pulse justified from the RTL.
- RHD-084 (MUST): Draw each functional group as a block from the bundled library (RHD-020, RHD-021). The label has exactly two centered lines: the group name on line 1 and `(FG of module_name)` on line 2, and the legend states that FG means functional group of the module own logic. A functional group sits one level below its module, like a child, so it appears on the page of depth d+1 for a module at depth d, only when d+1 does not exceed N (RHD-013). The module is shown as an enclosing frame (RHD-086) that contains its functional groups together with its child instances; no link arrows are drawn. A module at level N with own logic is marked `(not expanded; own logic)` in its function note and is not grouped.
- RHD-085 (MUST): Functional-group blocks follow all drawing rules for blocks and interfaces (RHD-045, RHD-048, RHD-049, RHD-052, RHD-056, RHD-057, RHD-058), including interface connectors between groups, between groups and child instances, and from groups to stubs for the module's own ports. Each group appears in the `Block Functions & Interfaces` table (RHD-046).
- RHD-086 (MUST): Draw a module that has children on the page (RHD-042) as one large bordered frame (library entry 32, solid black outline) that encloses its child blocks and functional-group blocks, as in a conventional block diagram of a module. The frame is a container, not a functional block: it is exempt from the fill ratios of RHD-052, its margin to the enclosed blocks follows RHD-053, and its size is set by the enclosed blocks and their routing. Interface stubs leave and enter the frame through its border (RHD-056, RHD-058).
- RHD-087 (MUST): Arrange the blocks of a frame compactly in two dimensions (rows and columns), placing blocks that exchange the most or the most important interfaces adjacent to each other, so that the whole frame fits a reasonably proportioned region (width to height ratio of the frame at most 3:1). With four or more blocks, blocks MUST NOT be laid out in a single row or a single column.

## E. Diagram structure

- RHD-040 (MUST): Save an editable multi-page diagrams.net XML file named `rtl_hierarchy.drawio` in the workspace unless the user gives another output path. Mermaid, images, and PDF MUST NOT replace it.
- RHD-041 (MUST): One page per hierarchy depth from 1 to the selected level N, named `01_LEVEL_1`, `02_LEVEL_2`, ..., ordered in the XML so tabs run left to right from level 1 to level N. No `00_TOP` page (a single block of the top module) is created, and no page is created for a depth deeper than N.
- RHD-042 (MUST): Each page for depth d >= 1 shows, for every module at depth d-1 that has children at depth d, that module as an enclosing frame (RHD-086) that contains its children: child instances and the functional groups of its own logic (RHD-084). A module without children at depth d is not repeated on that page.
- RHD-043 (MUST): Label every module block with exactly two centered lines: instance name on line 1 and `(module_name)` on line 2. The top module uses `TOP` on line 1 unless the user or source gives a better top instance label. Separate instances get separate blocks, even for the same module type. Functional-group blocks use the label of RHD-084. An enclosing frame carries the same two-line label (instance name, then `(module_name)`) INSIDE the frame in its upper-right corner, in a label zone that is reserved for it: the top margin of the frame is enlarged by the height of the label so that the zone lies below any trunk or connector that runs in the margin, to the left of any spine, and above every block. Nothing may touch the text (RHD-104).
- RHD-044 (MUST): Show the hierarchy by containment (RHD-086), not by arrows: instantiation links and parent-to-child arrows MUST NOT be drawn on pages that use enclosing frames. Draw the functional paths between visible blocks that are traceable through port maps and parent nets as interface connectors (completeness is governed by RHD-058). Speculative or indirect connections MUST NOT be drawn as direct.
- RHD-045 (MUST): Draw one connector per interface (RHD-074) between two blocks, not one line per wire. The connector is labeled with its short mnemonic (RHD-059) and its arrowhead follows RHD-049. The full interface name, category, active side, and every signal are given in the Interface Table (RHD-089). Do not label an interface AXI- or APB-compliant without RTL evidence.
- RHD-049 (MUST): The arrowhead of a connector points from the active side to the passive side. The active side is the logic that initiates or drives the transaction: a bus master or requester, the source of `valid` or `request`, a producer pushing into a FIFO, the source of an interrupt or start event, or the owner of host-written control. For an interface with signals in both directions (request and response, or bidirectional data) there is ONE connector whose arrowhead points from the initiating side to the responding side; the returned signals are listed in the Interface Table with their direction. When both sides initiate different transactions, they are different interfaces and get one connector each. Determine the active side from RTL behavior, record it in the interface table of `rtl_analysis.md`, and never infer it from the physical layout or port names alone. The library has no double-headed arrow, so a bidirectional signal group is never drawn with two arrowheads.
- RHD-058 (MUST): Every page draws all interfaces of every visible block with the outside of that block, with no omission of an interface listed in `rtl_analysis.md`. Each interface is drawn as one connector (RHD-045). When the peer block is visible inside the same frame, the connector joins the two blocks. When the peer is not inside the same frame (the outside world, a block of another frame, or a block on another page), draw the connector as a boundary stub that leaves the frame through its border and ends at a boundary text label (library entry 0) or pad (RHD-100) outside the frame; the stubs follow RHD-099, RHD-101 and RHD-102. On `01_LEVEL_1` every top-level port belongs to a drawn external interface. Examples of interfaces are APB, AXI, interrupt, control, status, clock/reset, FIFO, and memory interfaces (non-exhaustive; see `references/interface_groups.md`).
- RHD-059 (MUST): Give each interface that has two or more signals a unique mnemonic of at most 5 upper-case characters (for example `HRA`, `CSI`, `CLK`) that is used as its connector label. An interface that consists of exactly ONE signal has no mnemonic: its connector label, boundary label, pad label, and Interface Table ID are the signal name itself (for example `bus_off_on`, `tx_o`, `rx_sync`). The full name in the Interface Table is the standard name from `references/interface_groups.md` when the group matches an entry (with version only when proven, RHD-035); otherwise it is a descriptive name derived from the group function in `rtl_analysis.md`, marked `(custom)` or `(proposed group)` per RHD-078. The same identifier and name are used in `rtl_analysis.md`, the diagram, and the Interface Table. A boundary label of a multi-signal interface carries the mnemonic on line 1 and the signal names on the following lines.
- RHD-048 (MUST): Draw in two passes on each page: first place all blocks, then add every interface (RHD-058) as a connector with its mnemonic. Connectors MUST NOT be added before the blocks of that page are placed and sized.
- RHD-046 (MUST): Every page carries one `Block Functions & Interfaces` native draw.io table (title row, header row, one row per visible block; columns Block, Function, Source, Interfaces). The Function cell gives a thorough functional description of the block as a design engineer would explain it: what the block does, how it does it (algorithm, state sequencing, datapath, storage, timing), which operating modes and conditions affect it, and how it cooperates with the other blocks. It MUST NOT contain RTL signal, port, register, parameter or variable names; those belong to the Interface Table. The Source cell holds file and line references and the Interfaces cell the interface mnemonics of the block. The description is grounded in the RTL and states only what the RTL shows. Repeated instances of one module type are grouped in one row that lists their instance names, with instance-specific roles added when their wiring differs meaningfully. The table is widened or lengthened rather than clipping text or using a font below 18 pt.
- RHD-047 (MUST): Use solid black outlines for modules resolved in source and dashed black outlines for unresolved or external modules. State unresolved items in a note or the completion summary.

## F. Visual requirements

- RHD-050 (MUST): Black and white only: white fills, black borders, text, and connectors. No color accents, gray fills, gradients, or shadows.
- RHD-051 (MUST): All visible text, including block labels and titles, is 18 pt.
- RHD-052 (MUST): Keep every shape that contains text proportional to that text, so that no shape is large while its text is small. Text is fixed at 18 pt (RHD-051), so the shape is sized to the text and the font size MUST NOT be changed to compensate. Estimate the text box with the method in `references/sizing_guide.md` and apply these limits:
  - Rectangle (module block, label box): the text box fills at least 60% of the shape width and at least 50% of the shape height. Padding is 8 to 20 px per side. A two-line label stays intact on two lines.
  - Square: side length is at most the larger text-box dimension plus 40 px, and the text box fills at least 50% of the side in its larger dimension.
  - Circle or ellipse: the text box fits inside the inscribed rectangle (width at most 70% of the diameter) and fills at least 50% of the diameter in width. Diameter MUST NOT exceed 1.6 times the text-box diagonal.
  - Other library shapes (for example gate symbols): scale the whole group uniformly (RHD-022); the symbol height is between 2 and 4 line heights of 18 pt text, and its label is placed outside or inside according to the template.
  - Shapes with similar labels have similar sizes, and shapes are not stretched to fill the page or to align with neighbors.
  - Exceptions: the two description tables (RHD-046, RHD-089) are sized to their content and MUST NOT leave more than one blank text line of empty margin on any cell side; an enclosing frame is sized by its contents (RHD-086); IO pad symbols follow RHD-100. None of these is subject to the fill ratios above.
- RHD-053 (MUST): Pack blocks closely. The clear gap between two adjacent blocks starts at 1.5 block heights horizontally and 1.25 block heights vertically (90 px and 75 px for 60 px blocks) and is increased in steps of 10 px only when no routing satisfies RHD-079, RHD-097 and RHD-098 at the smaller gap. The final gaps SHOULD NOT exceed 2.5 block heights horizontally and 2 block heights vertically (150 px and 120 px); a larger gap requires a stated reason in the delivery report. The margin between the frame and the nearest enclosed block is 40 px (about 0.7 block height); it grows in steps of 10 px, never beyond 60 px, only when a routing under RHD-079, RHD-097 and RHD-098 or a label under RHD-104 does not fit at the smaller margin; the report states the final margin. Align blocks on a common grid of rows and columns inside a frame.
- RHD-097 (MUST): Prefer connectors that do not cross any other connector. When a connector cannot be routed without crossing within the bend limit of RHD-079, it MAY cross one other connector; only when that is also impossible MAY it cross two; no connector crosses more than two. Search progressively: vary the row and column gaps (RHD-053), the connector routing order, and the port assignment on each block side, and keep the arrangement with the lexicographically smallest (total crossings, maximum crossings per connector, total bends, frame area) that satisfies RHD-079. Every remaining crossing uses an arc jump (RHD-057).
- RHD-098 (MUST): A connector between two blocks that face each other (adjacent in the same row or column, with an unobstructed corridor between their facing sides) MUST be a single straight line with no jog or step. To make this possible, assign the ports of such a connector at the same coordinate on both facing sides, ordering neighbouring ports on each side consistently with the positions of their peers. Straight facing connectors are routed first and their corridors are kept free of labels and other connectors.
- RHD-099 (MUST): Place the boundary labels and pads of functionally related external interfaces on the same side of the frame, adjacent to each other and in the order of the blocks they serve: for example the receive and transmit pins of one serial bus, or the interrupt, status and clock outputs. Choose the side by function and block position wherever the block positions allow, for example host bus on one side, serial-bus pins on one side, clock/reset entry on one side. Each stub stays straight (RHD-101); pins of one protocol remain separate interfaces (RHD-100).
- RHD-100 (MUST): Dedicated off-chip line interfaces are drawn separately, one boundary symbol per pin. A dedicated line is a single-pin or paired signal that connects directly to an IO pad, a pin of the chip, or an external transceiver or PHY, and carries a serial or point-to-point protocol: for example the receive and transmit lines of CAN, UART (RXD, TXD, RTS, CTS), SPI (SCLK, MOSI, MISO, chip select), I2C (SDA, SCL), JTAG, LIN, or a plain GPIO pin. Each such pin gets its own stub and its own IO pad symbol (library entry 5, the square with two diagonals, scaled uniformly to 30 x 30 px, about half the size of a 60 px block, so that the pad matches the other shapes; pads are exempt from the symbol-height range of RHD-052), with the mnemonic and pin name in a text label next to the pad. They are NOT merged into one interface of RHD-074, even when they belong to one protocol; pins of one protocol are placed on the same side and adjacent to each other (RHD-099). A multi-pin bus that the host drives as a single access (for example an address, data and strobe bus) stays ONE interface of RHD-074 and is drawn with a text label, not with pads. Control, status, interrupt, clock and reset pins are drawn with text labels.
- RHD-101 (MUST): Every boundary interface (an interface between a block inside a frame and the outside of that frame, or between a lone top block and the outside) is drawn as a straight line without any bend. The boundary label or pad is aligned with the port: the stub leaves the block perpendicular to its side, crosses the frame border perpendicularly, and ends at the label or pad. When several stubs share one side, the stubs keep the straight shape and the labels are staggered instead: the outermost stubs of the side end early with their labels placed beside the stub end, and the inner stubs are longer with their labels placed beyond the end, so that no stub passes through a label or pad and no label overlaps another. Ports that cannot satisfy this on a side are moved to another side of the block before a bend is allowed. Boundary connectors do not count against the bend limit of RHD-079.
- RHD-102 (MUST): A boundary signal group that feeds several blocks inside the same frame (typically clock and reset) is drawn as ONE distribution tree with ONE boundary point: a single boundary label and entry stub, and from the stub a trunk that runs inside the frame margin (12 px inside the border) with one branch per target block, each branch ending in an arrowhead at the block port. Branches of the same tree may overlap along the shared trunk, and they do not count as crossings of each other. Branches choose the side of each block that is free of other connectors and keep the number of bends to the minimum that the margin routing allows; the tree is exempt from the bend limit of RHD-079 but not from RHD-056 and RHD-057, so every crossing with a connector of another interface uses an arc jump and is counted once per physical crossing point (RHD-097). The entry stub itself is a straight boundary stub (RHD-101). When the tree must run along a margin that carries boundary stubs of other interfaces, the crossings are accepted (arc jumps, counted per physical point) instead of splitting the tree into several entry points or enlarging the frame; the user confirmed this choice on 2026-10-16.
- RHD-054 (MUST): Place the two description tables below the diagram of the page, never inside a frame or block, one above the other, with the Block table first. Expand the page rather than crowd blocks, connectors, or tables.
- RHD-055 (MUST): Choose page size and orientation to fit the diagram and the tables with balanced margins and no clipping, and place connector labels so they overlap neither blocks, other labels, nor other connectors. Connector routing is governed by RHD-056, RHD-057 and RHD-079.
- RHD-088 (MUST): Turn the editor grid off on every page of the generated file (`grid="0"` in every `mxGraphModel`), so that the diagram opens without a grid background. Block and connector coordinates MAY still follow a layout grid internally.
- RHD-089 (MUST): Below the `Block Functions & Interfaces` table, place one `Interface Table` native draw.io table (title row, header row) with one row for every drawn mnemonic (internal and external), with the columns ID, interface name, category (standard protocol, handshake, custom), active side to passive side, and signals. The Signals cell lists EVERY signal name of the interface, with its width where wider than one bit, grouped by direction when the interface carries signals both ways (for example `A -> B: ...; B -> A: ...`) and with level/pulse tags where known. Abbreviations such as `etc.`, `...`, `*`, or ranges such as `name_0..12` MUST NOT replace the individual names; signals left unconnected in the RTL are listed as `(open)`. Text is 18 pt; column widths are chosen so that no cell text is clipped.
- RHD-079 (MUST): Route connectors for the fewest bends and crossings, and keep them short. Each interface connector inside a frame has at most 4 bends (boundary stubs follow RHD-101 and distribution trees RHD-102). At most 10% of the connectors on a page MAY have 5 bends, and none has more than 5. Choose the block arrangement (RHD-087) and the side of each port so that connected blocks are adjacent and straight or L-shaped routes are possible, and assign neighboring ports on a block side in the order of the positions of their peers so that connectors do not cross at the ports. Remaining crossings follow RHD-057.
- RHD-056 (MUST NOT): Let any connector pass through the interior of a block, label, pad, or table. A connector may touch only the borders of the blocks it joins. The only permitted crossing of an enclosing frame border is by an external-interface connector (RHD-058) on its way to its boundary label outside the frame. Route around other blocks with waypoints or orthogonal segments, and increase block spacing or reorder blocks when no clean route exists. Reduce the number of crossings by layout choice first.
- RHD-057 (MUST): When two connectors must cross, make one of them hop over the other using the draw.io line-jump option: set `jumpStyle=arc` (with `jumpSize` of the editor default or a stated value) on the connector that crosses, so the lines visibly pass without touching. Connectors MUST NOT cross without a jump, merge, or overlap along a shared segment, because that would suggest an electrical connection that does not exist; the only exception is the shared trunk of one distribution tree (RHD-102). Apply the jump on every crossing.

- RHD-104 (MUST NOT): Let any line, border, symbol, or other text cover or touch text. No connector, trunk, spine, frame border, pad, block outline, or table edge passes through or touches the text box of a label, a frame label, a block label, or a table cell, and no two text boxes overlap. The only contact allowed is the end of the stub that belongs to a label, where the arrow tip ends on the label border. The geometry check of `scripts/drawio_geometry_check.py` reports violations and MUST be run before delivery (RHD-061, RHD-062).

## G. Validation and delivery

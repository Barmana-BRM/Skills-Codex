## 1. 评审顺序

按以下顺序检查，避免只盯局部像素：

1. 语义是否一致
2. 是否复用已有组件或模式
3. Token 是否稳定
4. 组件状态和变体是否完整
5. 页面组合是否遵守同一规则
6. 是否有合理的场景化例外

如果用户提供设计系统，以用户系统为准；平台规范和通用规律只用于指出风险或缺口。

## 2. Token

检查：

- 颜色是否按角色组织，而不是按页面或随机色值组织。
- 文字颜色、背景、边框、填充、功能色和交互状态是否复用语义 Token。
- 字体家族、字号、字重、行高和字间距是否形成可解释的文字角色。
- 间距是否来自有限序列；离群值是否有内容或光学理由。
- 圆角、描边、阴影、透明度、模糊和层级是否有稳定规则。
- 尺寸 Token 是否区分视觉尺寸、容器尺寸和交互热区。
- 深浅主题、品牌主题和高对比模式是否维持语义，而不是简单反色。

不要因为数值没有落在 4px/8px 倍数就直接判错。先确认当前系统采用的基础单位与光学补偿策略。

## 3. 组件

### 复用与变体

- 相同结构是否误建为多个一次性组件。
- 同一组件的尺寸、层级、语义和状态是否用变体表达。
- 变体属性是否正交，避免把尺寸、状态、主题和内容混在一个模糊命名中。
- 组件是否允许必要的内容增长，又避免无限自由导致失控。
- 实例是否大量解除绑定或深度覆盖，暗示主组件不适配真实需求。

### 状态完整性

检查适用的默认、悬停、焦点、按下、选中、禁用、加载、成功、错误和空状态。状态之间要同时满足：

- 可区分
- 语义一致
- 不只依赖颜色
- 不改变布局到引发跳动
- 与平台输入方式匹配

### 内部结构

- 图标、标签、前后缀、帮助文本和错误文本的间距是否稳定。
- 内边距、最小高度、文本换行和内容对齐是否能覆盖真实场景。
- 嵌套组件是否出现重复边框、重复阴影或圆角冲突。
- 组件层级是否与 z-index/elevation 语义一致。

## 4. 模式与跨屏一致性

- 相同任务是否使用相同入口、术语、步骤和反馈。
- 相同信息结构是否使用相同页面模板。
- 不同语义是否被错误套成同一个组件，只为了视觉统一。
- 页面间导航、标题、主操作位置和返回逻辑是否稳定。
- 表单、列表、详情、搜索、筛选、空状态和异常状态是否形成复用模式。
- 跨端一致性应保留产品心智，同时尊重各平台惯例；不要求像素级完全相同。

## 5. Figma 文件健康度

有 Figma 元数据时检查：

- 页面、Frame、组件和图层命名是否能表达角色。
- 是否使用 Auto Layout、约束或布局网格支撑内容变化。
- 相同元素是否来自同一组件实例。
- 本地样式或变量是否复用，是否出现大量近似色、近似字号和近似间距。
- 组件属性和变体是否有清晰命名。
- 图标是否保持统一网格与矢量结构。
- 是否存在隐藏图层、离画布节点、无意义分组和过深嵌套。

文件整洁度是协作和维护问题，不能凌驾于用户体验。只有当它增加错误、交付成本或系统漂移时，才提高优先级。

## 6. 响应式与内容韧性

- 组件应在最短、最长和多语言内容下保持语义与布局。
- 检查窄屏、宽屏、窗口缩放、横竖屏和系统字体变化。
- 栅格、边距和列数可以变化，但信息优先级应稳定。
- 避免固定高度、绝对定位和理想文本长度支撑主要布局。
- 明确哪些区域固定、伸缩、换行、折叠、滚动或重排。
- 表格、图表、地图等二维内容可局部滚动，但不应拖累整个页面。

## 7. 问题合并方式

发现多个页面使用相同错误样式时，输出一条系统性问题：

- 根因：例如 `text-secondary` 对比不足。
- 影响范围：列出页面/组件。
- 系统改法：修改 Token 或主组件。
- 局部例外：说明哪些场景不能直接批量替换。
- 回归检查：列出深浅主题、状态和受影响组件。

优先级通常遵循：

1. 语义冲突和无障碍风险
2. 高频核心组件
3. 跨页面系统漂移
4. 单页局部不一致
5. 文件整理与命名

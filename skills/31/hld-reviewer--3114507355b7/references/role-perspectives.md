# 角色视角审查要点

本文档定义了第三道门「风险驱动的角色增量审查」中各专业角色的审查要点。

必须先服从 `../../../references/review-boundaries.md`。角色视角不产生决策权限；以下表格是**有前提的风险假设**，不是自动 findings。只有本轮范围、有效需求/授权、具体失败与影响均成立时，才按真实严重性分级；证据不足列 gap，边界变化列 scope decision，未来优化列 P2。所有 P2 数量均不阻断。

有限变更只启用相关视角。不得从示例直接要求新存储、PDP、DLQ、缓存、功能开关、查询 API、监控或重放平台。先检验既有机制是否已经满足目标；新增常态依赖、维护成本、数据/失败语义仍需原始授权。

---

## 角色启用规则

**不是每个 HLD 都需要全部角色审查。根据风险特征按需启用：**

| 风险特征 | 启用角色 |
|----------|----------|
| 涉及敏感数据、认证、授权 | Security |
| 涉及数据迁移、Schema 变更 | DBA |
| 高并发、性能敏感场景 | SRE/Performance |
| 跨团队、跨系统依赖 | Architect |
| 复杂测试场景 | QA |

**基础审查（必选）**：Tech Lead + Senior Engineer（已在第二道门覆盖）

## Security 视角

### 触发条件
- HLD 涉及用户认证/授权
- HLD 涉及敏感数据（PII、支付、健康等）
- HLD 涉及外部系统集成
- HLD 涉及 API 暴露给外部

### 审查要点

#### 1. 认证设计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 认证机制是否明确？ | 未说明使用什么认证方式 | P1 |
| 是否使用安全的认证协议？ | 使用明文密码传输 | P0 |
| 会话管理是否安全？ | 会话 ID 可预测 | P0 |
| Token 存储是否满足既定威胁模型？ | 存在可证实的泄漏链；不能仅凭 localStorage 一词判级 | 按影响 |
| 密码策略是否符合批准的认证要求？ | 与已批准策略冲突；不因缺字符复杂度自动加规则 | 按影响 |

#### 2. 授权设计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 权限模型是否明确？ | 未说明权限检查机制 | P1 |
| 是否有越权风险？ | 仅靠前端控制权限 | P0 |
| 是否遵循最小权限原则？ | 默认给予过高权限 | P1 |
| 人/机器主体及权限来源是否保持批准边界？ | 后台任务新增用户会话/PDP 依赖，或删除已批准授权检查 | 缺陷 / Scope decision |

#### 3. 数据保护
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 敏感数据是否按其类别保护？ | 已证实密码明文泄露风险；不将元数据等同凭据值 | 按影响 |
| 传输是否满足明确的信任边界？ | 存在明文跨不可信边界暴露，而非仅凭 HTTP 字样 | 按影响 |
| 日志是否脱敏？ | 日志中包含完整手机号 | P1 |
| 数据是否有访问控制？ | 任何服务都能读取用户表 | P1 |

#### 4. 安全审计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 关键操作是否有要求的审计证据？ | 已批准追溯要求无法满足，且既有记录不足 | 按影响 |
| 审计防篡改与删除策略是否一致？ | 违反批准审计/保留规则；不能自动要求永久不可删 | 按影响 |
| 异常行为是否有告警？ | 无登录失败告警 | P2 |

#### 5. 合规性
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 是否符合适用的数据保护要求？ | 先确认适用范围及有效依据，不能假定所有项目都适用 GDPR | 按影响 |
| 是否有要求的数据删除机制？ | 违反已批准保留/删除语义 | 按影响 |

### 典型问题示例

```markdown
**问题**：用户密码使用 MD5 哈希存储
**角色**：Security
**严重度**：P0
**证据**：HLD 4.2 节 "密码使用 MD5 加密存储"
**有效依据**：已批准登录方案要求抗离线破解的密码存储；确认这里是密码值，而非非敏感摘要
**风险**：MD5 已不安全，容易被彩虹表破解
**最小建议**：沿用系统已批准的安全密码哈希实现；若需更换算法/迁移历史凭据，单独确认兼容影响，不顺带新增登录平台
```

## DBA 视角

### 触发条件
- HLD 涉及数据库 Schema 变更
- HLD 涉及数据迁移
- HLD 涉及大数据量处理
- HLD 涉及新建数据库/表

### 审查要点

#### 1. 数据模型设计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 实体设计是否合理？ | 过度范式化导致查询复杂 | P2 |
| 关系设计是否正确？ | 多对多关系缺少中间表 | P1 |
| 是否考虑已批准范围内的数据增长？ | 目标负载证明确实超过现有能力，不按臆测未来亿级规模扩展 | 按影响 |

#### 2. Schema 变更
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 变更是否向后兼容？ | 删除列导致旧版本报错 | P0 |
| 是否有迁移脚本？ | 只描述目标状态无迁移步骤 | P1 |
| 是否有符合已批准要求的恢复路径？ | 不可逆变更却无获批恢复/前向修复方案 | 按影响 |
| 迁移方式是否符合停机承诺？ | 仅在不允许停机时，停服才构成违约；不自动要求在线迁移 | 按影响 |

#### 3. 数据迁移
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 迁移数据量评估？ | 未评估迁移时长 | P1 |
| 迁移失败如何处理？ | 无中断恢复机制 | P1 |
| 数据一致性如何保证？ | 迁移过程中数据可能不一致 | P1 |
| 是否有数据验证？ | 迁移后无校验步骤 | P1 |

#### 4. 索引设计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 关键查询是否有索引支撑？ | 高频查询走全表扫描 | P1 |
| 索引是否过多？ | 写入性能下降 | P2 |
| 是否有无用索引？ | 存在从未使用的索引 | P2 |

#### 5. 性能考量
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 大表查询是否有优化？ | COUNT(*) 全表扫描 | P1 |
| 容量是否有真实瓶颈证据？ | 行数本身不证明必须分库分表，优先既有索引/查询方案 | 按影响 |
| 是否有慢查询风险？ | 复杂 JOIN 无优化 | P2 |

### 典型问题示例

```markdown
**问题**：用户表新增 NOT NULL 列，无默认值
**角色**：DBA
**严重度**：P0
**证据**：HLD 3.2 节 Schema 变更 "ALTER TABLE users ADD COLUMN phone VARCHAR(20) NOT NULL"
**有效依据**：该表已有数据，批准方案要求保存这些行；证实新列无默认值/合法历史来源
**风险**：现有数据无法满足 NOT NULL 约束，迁移会失败
**建议**：
1. 先添加列允许 NULL
2. 使用获批、可证明来源回填；没有依据不能猜造手机号/默认业务数据
3. 再修改为 NOT NULL
```

## SRE/Performance 视角

### 触发条件
- HLD 涉及高并发场景
- HLD 有明确的性能要求
- HLD 涉及关键业务路径
- HLD 涉及资源密集型操作

### 审查要点

#### 1. 性能目标
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 性能目标是否明确？ | 只说"快"，无具体指标 | P1 |
| 目标是否与 PRD 对齐？ | PRD 要求 100ms，HLD 设计 500ms | P0 |
| 是否有基线数据？ | 无法衡量性能是否达标 | P2 |

#### 2. 容量规划
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 是否有容量评估？ | 不知道能支撑多少 QPS | P1 |
| 是否考虑峰值场景？ | 只考虑平均负载 | P1 |
| 容量方案是否满足批准目标？ | 单实例实测达不到目标；无水平扩展本身不是缺陷 | 按影响 |

#### 3. 高可用设计
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 单点风险是否符合可用性承诺？ | 具体故障违反已批准 SLO；不自动引入备份服务 | 按影响 |
| 依赖失败语义是否符合批准边界？ | 需要恢复却不能恢复；已批准 fail-closed 不能擅改降级放行 | 按影响 |
| 下游故障是否有受控边界？ | 现有超时/容量限制仍不足，有证据再讨论最小修复 | 按影响 |
| 突发流量是否超过批准容量？ | 已证实目标负载会击穿现有机制，不预设必须新限流平台 | 按影响 |

#### 4. 故障恢复
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 故障检测是否及时？ | 故障 10 分钟后才发现 | P1 |
| 恢复步骤是否明确？ | 没有故障恢复 SOP | P1 |
| 数据恢复能力如何？ | 无法恢复到故障前状态 | P1 |

#### 5. 运维友好性
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 是否便于问题定位？ | 日志不足以定位问题 | P2 |
| 是否便于配置变更？ | 改配置需要重启服务 | P2 |
| 是否便于版本管理？ | 无法快速识别运行版本 | P2 |

### 典型问题示例

```markdown
**问题**：缓存失效时直接穿透到数据库
**角色**：SRE
**严重度**：P1
**证据**：HLD 5.1 节缓存设计，未提及缓存击穿保护
**待核实**：目标并发、缓存失效时实际数据库容量和既有背压证据；缺这类证据不能仅凭“未提及”判 P1
**风险成立时的最小建议**：先评估既有请求合并/容量限制是否足够；不自动新建二级缓存，不将有限 TTL 改为永不过期
```

## Architect 视角

### 触发条件
- HLD 涉及跨团队依赖
- HLD 涉及跨系统集成
- HLD 涉及架构重大变更
- HLD 影响多个现有系统

### 审查要点

#### 1. 架构一致性
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 是否符合企业架构原则？ | 违反微服务边界原则 | P1 |
| 是否与现有系统设计一致？ | 与其他服务风格迥异 | P2 |
| 是否遵循既定模式？ | 重新发明已有解决方案 | P1 |

#### 2. 系统边界
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 系统边界是否清晰？ | 职责与其他系统重叠 | P1 |
| 是否有有害循环依赖？ | 证明同步等待/启动循环导致失败，不能只看双向箭头 | 按影响 |
| 依赖方向是否在批准边界内？ | 新依赖改变职责、可用性和维护成本 | 缺陷 / Scope decision |

#### 3. 跨系统影响
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 对上游系统的影响？ | 获批协作不自动是 P1；检查遗漏的具体兼容义务 | 按影响 |
| 对下游系统的影响？ | 获批适配不自动是 P1；检查未批准支持变化 | 按影响 |
| 接口契约是否明确？ | 接口定义不清晰 | P1 |

#### 4. 演进性
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 是否便于后续扩展？ | 设计过于定制化 | P2 |
| 是否便于独立部署？ | 多个模块紧耦合 | P1 |
| 是否便于独立演进？ | 改动影响范围过大 | P2 |

### 典型问题示例

```markdown
**问题**：新服务直接访问其他团队的数据库
**角色**：Architect
**严重度**：P0
**证据**：HLD 3.3 节 "直接查询用户中心数据库获取用户信息"
**有效依据**：项目已批准用户中心独占数据 owner、跨团队只能走既有 API；若无该依据先待澄清，不把通用微服务偏好当规范
**风险**：违反服务边界原则，数据库变更会直接影响本服务
**最小建议**：使用现有已批准 API；若现有接口不能满足，不擅自要求新增接口或服务，列边界内替代及待决定项
```

## QA 视角

### 触发条件
- HLD 涉及复杂业务逻辑
- HLD 涉及多系统集成
- HLD 涉及状态机/流程
- HLD 测试难度较高

### 审查要点

#### 1. 可测试性
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 模块是否便于单测？ | 模块间强耦合 | P2 |
| 关键行为是否可验证？ | 仅不能 Mock 不构成缺陷；真实隔离验证可能已足够 | 按影响 / Evidence gap |
| 是否有测试困难点？ | 具体必要验收无法观察，不等于必须新建测试接口 | 按影响 / Evidence gap |

#### 2. 测试策略
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 单元测试策略是否可行？ | 代码难以单元测试 | P2 |
| 集成测试策略是否可行？ | 依赖环境难以搭建 | P1 |
| E2E 测试策略是否可行？ | 测试场景过于复杂 | P2 |

#### 3. 测试数据
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| 测试数据如何准备？ | 无法构造测试数据 | P1 |
| 测试环境如何隔离？ | 测试会污染其他数据 | P1 |

#### 4. 验收标准
| 检查项 | 问题 | 严重度 |
|--------|------|--------|
| HLD 能否验证 PRD 验收标准？ | 部分验收标准无法测试 | P1 |
| 性能验收如何进行？ | 无性能测试方案 | P2 |

### 典型问题示例

```markdown
**问题**：异步消息处理无法验证消息是否正确消费
**角色**：QA
**严重度**：P1
**证据**：HLD 4.5 节消息队列设计
**有效依据**：已批准验收要求证明持久化完成后确认；现有测试只替换为计数器，未经过生产事务边界
**最小建议**：复用生产消费者及既有持久化读回做隔离负例，观察提交/回滚；不为测试新增查询 API、监控服务或永久模拟工具
```

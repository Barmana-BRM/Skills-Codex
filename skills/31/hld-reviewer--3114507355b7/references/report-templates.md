# HLD 审查报告与准出证书模板

先遵循 `../../../references/review-boundaries.md`。完整报告/证书只用于 `formal_design`；有限增量使用末尾模板，可直接回复或更新既有请求，不强制新文件。不要预填通过、100%覆盖或独立 reviewer 身份。技术判断、设计授权、执行许可分别输出。

## 正式审查报告模板

```markdown
# HLD 审查报告

## 基本信息

| 项目 | 内容 |
|------|------|
| HLD / 本轮版本 | [路径、实际版本] |
| PRD / API / Guardrails / ADR | [相关有效基线及版本] |
| 原始批准来源 | [谁有权、批准了什么；引用原始记录，不以 reviewer 旧 comment 自证] |
| 模式与范围 | formal_design；[本轮完整对象/整改 ID、未变范围] |
| 时间 / 轮次 | [实际时间、第 N 轮] |
| 风险 / 角色 | [有依据的风险、启用角色及证据] |
| technical_verdict | APPROVED / CHANGES_REQUIRED / EVIDENCE_BLOCKED |
| scope_status | WITHIN_APPROVED_SCOPE / DECISION_REQUIRED |

## 第一道门：批准范围与漂移

### 需求覆盖

| 基线条目 | 验收/边界 | HLD 位置 | 状态 | 未覆盖/待澄清说明 |
|----------|-----------|----------|------|-------------------|
| REQ-* / 已批准决定 | [要求] | [章节/行号] | 已覆盖 / 部分 / 未覆盖 / 未知 | [已覆盖填 —，其他说明原因] |

- [实际覆盖 x/y、分母范围；1:N 分配范围与已设计覆盖分开]
- [追溯 metadata / lint / RTM 实际结果与影响；无 block 的已有等价映射]
- [遗漏、语义漂移、未批准职责/依赖变化的结论与证据]
- [仍依赖未决事项的部分，以及可继续审查的独立部分]

## Findings

### P0 / P1 缺陷

| 稳定 ID / 级别 | 当前失败与影响 | 有效依据 / 证据 | 最小修复及边界变化 |
|---------------|----------------|----------------|--------------------|
| [原 ID / P0或P1] | [具体失败、影响] | [批准来源 + HLD位置] | [边界内最小修复；需新授权则转 Decision Gates] |

## Missing Info / Questions

- [必要事实/可行性缺口、最小证据、影响的结论；无则写“无”]
- [原 reviewer 漏审/错误归因及受影响结论；不将自己旧错误包装为 Dev 新缺陷]

## Decision Gates

- [旧行为 → 新行为、产品/架构影响、边界内选项、推荐、有权 Owner、缺少的具体授权；无则写“无”]
- [若作者 note/旧 comment 被循环当成批准，注明原始来源，撤回具体错误“已批准”表述，不暗改无关基线]

## Optional Improvements

- [P2 可选建议；数量永不阻断，不自动进入下轮；无则写“无”]

## 技术与证据覆盖

| 维度 | 已审证据 / 实际结果 / N/A 理由 |
|------|-------------------------------|
| 架构职责、决策与替代方案 | [结果] |
| 技术栈、复用与维护成本 | [结果] |
| 接口、数据及生命周期 | [结果] |
| 新旧兼容、发布与恢复 | [结果] |
| 可观测性、风险和可测试性 | [结果] |
| 专业角色增量 | [启用理由及结果] |
| 实际管理入口与执行器 | [真实 parser/client/配置能力证据；模拟/自写 compiler 的局限] |

## 放行结论

| 门槛 | 实际结果 |
|------|----------|
| P0 / P1 均为零 | [数量与关闭证据] |
| 必要证据缺口关闭 | [实际] |
| 范围具有有效原始授权 | [实际] |
| 本轮正式覆盖完整 | [实际，未审必须披露] |

technical_verdict：[APPROVED / CHANGES_REQUIRED / EVIDENCE_BLOCKED]
scope_status：[WITHIN_APPROVED_SCOPE / DECISION_REQUIRED]
执行许可：[本轮明确授权的操作；技术通过不自动授权实施、push、CI、策略发布或部署]

## 历程与下一步

| 轮次 | 原 ID | 变化 / 证据 / 结论 |
|------|-------|--------------------|
| [N] | [原 finding] | [实际整改及关闭依据] |

- [最小修复、取证或 Owner 决策；范围内阻断关闭即停止，不增加产物清单]
```

## 正式准出证书模板

仅在正式范围覆盖完成、P0/P1 为零、必要证据与授权无缺口时生成。以下字段需按事实填写，不是预设成功断言；有限修复不签全量证书。

```markdown
# HLD 准出证书

## 基本信息与对象绑定

- HLD：[路径及实际审查版本/提交]
- 批准依据：[PRD/API/Guardrails/ADR 的版本、原始 Owner 批准及范围]
- 时间/轮次：[实际]
- technical_verdict / scope_status：[经验证的结论]

## 一致性与门槛确认

- [范围内需求覆盖比例及证据，遗漏/曲解/未批准扩张的检查结果]
- [P0/P1 实际为零及原 finding 关闭依据]
- [必要 evidence gap / scope decision 的关闭来源]
- P2 可选，不参与准出门槛。

## 审查历程与覆盖

- [各轮实际结论、三道门实际覆盖、角色选择及 N/A 理由]
- [正式覆盖未完成则不能生成本证书，不能把未审写成通过]

## 审查者与权限边界

- Reviewer：[实际执行者、可核实的独立性；未独立评审不能声称独立]
- 本证书仅证明上述正式 HLD 范围的设计评审结论；实施、push、CI、策略发布、共享数据写入和部署仍需各自明确授权。
- 文件名哈希或自制 PASSED 签章不能证明审批或 reviewer provenance。
```

## 有限增量 / 整改复审模板

```markdown
模式：bounded_change
对象/范围：[请求、相关批准基线、原 finding ID、明确不变的边界]
批准来源：[谁在什么范围批准了什么，引用原始记录]
结果：[原 ID 关闭证据；缺陷 / 最小 evidence gap / scope decision 分开；无则写无]
technical_verdict：[APPROVED / CHANGES_REQUIRED / EVIDENCE_BLOCKED]
scope_status：[WITHIN_APPROVED_SCOPE / DECISION_REQUIRED]
执行许可：[实际明确授权，不由技术通过推导]
下一步：[最小动作；必要时向有权 Owner 解释旧/新行为与推荐]
可选项：[P2 不阻断，不自动续轮]
```

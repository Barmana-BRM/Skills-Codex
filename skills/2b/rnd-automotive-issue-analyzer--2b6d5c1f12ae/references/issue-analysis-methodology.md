# 问题分析方法论知识库

> **核心警告**：不知道就是不知道，绝对不要胡诌！错误的结论比没有结论更危险。

## 一、致命错误：必须避免的思维陷阱

### 错误 1：表面现象陷阱 (Symptom vs Root Cause)

**错误思维**：
```
看到现象 → 发现可疑行为 → 立即判定为根因
```

**正确思维**：
```
看到现象 → 收集所有证据 → 多假设验证 → 选择证据最强的假设
```

**教训**：混淆症状和根因是最常见的错误
- **症状**: 用户可见的问题表现
- **根因**: 导致症状的底层原因

### 错误 2：证据盲点 (Evidence Blindness)

**常见忽略的关键证据**：
```log
# 主线程阻塞 - 高权重
Long monitor contention with owner xxx at xxx for Xs

# 帧率问题 - 高权重
Choreographer: Skipped XXX frames!

# I/O阻塞 - 高权重
QueuedWork.processPendingWork() for Xs
```

**搜索策略**：优先搜索高权重性能关键词，而非随机搜索

### 错误 3：数学验证缺失

**必须做数学验证**：
```
阻塞时间 × 帧率 = 跳帧数
2.746秒 × 60fps = 164.76帧 ≈ 实际跳过162帧
误差 < 2% → 完美吻合！
```

数学验证是最强的证据，可以排除巧合，确认因果关系。

### 错误 4：单一假设陷阱

**错误流程**：
```
发现可疑现象 → 推断是根因 → 结束分析 ✗
```

**正确流程**：
```
列出所有可疑现象 → 提出多个假设 → 用证据逐一验证/排除 → 选择证据最强的假设 ✓
```

### 错误 5：置信度误判

**置信度必须诚实反映证据充分程度**：
- 没有明确证据链时，不应给出高置信度
- 时间不匹配、因果关系薄弱时，要降低置信度

## 二、五步分析法（必须严格执行）

### Step 1：信息收集 [30%时间]

**问题陈述 5W1H**：
- **What**: 具体现象
- **When**: 时间窗口
- **Where**: 影响范围
- **Who**: 相关组件
- **Why**: (待分析)
- **How**: (待分析)

**日志收集策略**：
- ERROR级别日志
- WARNING级别日志
- 性能相关日志
- 生命周期日志

**关键性能信号搜索**（必查）：
- [ ] "Long monitor contention"
- [ ] "Skipped frames"
- [ ] "ANR"
- [ ] "GC paused"
- [ ] "QueuedWork"
- [ ] "Blocked"
- [ ] "timeout"
- [ ] "fence"

### Step 2：证据分类与权重 [20%时间]

**证据金字塔**（按权重从高到低）：

```
                数学验证完美吻合
                (2.746s × 60fps = 162帧)
                ⬆ 最高权重 ⬆
            ━━━━━━━━━━━━━━━━━━━━━
           系统级性能日志
           (QueuedWork, Choreographer)
           ⬆ 高权重 ⬆
       ━━━━━━━━━━━━━━━━━━━━━━━━
      Framework源码已知行为
      (ActivityThread源码)
      ⬆ 高权重 ⬆
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 时间序列完美吻合
 (事件A → 事件B)
 ⬆ 中高权重 ⬆
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
应用层行为观察
⬆ 中低权重 ⬆
```

**证据分类**：
- 🔴 关键证据 (Smoking Gun)
- 🟡 重要证据 (Strong Evidence)
- ⚪ 次要证据 (Weak Evidence)

### Step 3：多假设生成 [15%时间]

**必须至少提出3个假设**：
```markdown
假设A: [描述]
- 支持证据: ...
- 反驳证据: ...
- 初步置信度: X%

假设B: [描述]
- 支持证据: ...
- 反驳证据: ...
- 初步置信度: X%

假设C: [描述]
- 支持证据: ...
- 反驳证据: ...
- 初步置信度: X%
```

**确保假设覆盖不同层面**：
- 应用层问题
- Framework层问题
- 系统层问题
- 硬件/环境问题

### Step 4：假设验证 [25%时间]

**因果链完整性检查**：
```
原因 → 步骤1 → 步骤2 → ... → 结果
  ↓      ↓       ↓            ↓
证据1   证据2   证据3        证据N

每一步都必须有证据支持！
```

**数学验证**：
- 计算相关数值
- 验证时间吻合度
- 验证数量吻合度
- 误差分析

**反证检查**：
- "有没有证据能推翻这个假设？"
- "有没有其他更合理的解释？"

### Step 5：置信度评估与输出 [10%时间]

**置信度计算**：
```
基础置信度: 50%

加分项:
+ 完整因果链 (+20%)
+ 关键证据存在 (+30%)
+ 数学验证吻合 (+20%)
+ 源码/文档支持 (+20%)
+ 无反证 (+10%)

减分项:
- 证据链不完整 (-20%)
- 存在反证 (-30%)
- 无数学验证 (-10%)
```

**不确定性说明**：
- 明确哪些部分是确定的
- 明确哪些部分是推测的
- 说明需要什么额外证据

## 四、车载系统问题模式速查

### 显示问题模式

| 特征 | 根因 | 关键日志 |
|------|------|----------|
| 黑屏 | 电源/背光/显示驱动/SurfaceFlinger | HWC, HDMI, SurfaceFlinger |
| 白屏 | 显示驱动初始化失败/信号异常 | display driver, init |
| 闪屏 | 帧率不稳定/GPU问题/电源干扰 | Choreographer, GPU |
| 花屏 | 内存损坏/DMA错误/信号干扰 | memory, DMA, signal |

### 稳定性问题模式

| 特征 | 根因 | 关键日志 |
|------|------|----------|
| ANR | 主线程阻塞/Binder超时/死锁 | traces.txt, Blocked |
| JE | 空指针/类型转换/数组越界 | Exception, NPE |
| NE | 内存访问违规/段错误/野指针 | tombstone, SIGSEGV |
| 死机 | System Server崩溃/Watchdog超时 | Watchdog, system_server |

### 性能问题模式

| 特征 | 根因 | 关键日志 |
|------|------|----------|
| 卡顿 | CPU高/GC频繁/IO阻塞 | Skipped frames, GC |
| 内存问题 | OOM/内存泄漏/碎片 | OutOfMemory, Low memory |
| 启动慢 | 冷启动/预加载/并行初始化 | boot, init, zygote |

### 多系统问题模式

| 特征 | 根因 | 关键日志 |
|------|------|----------|
| 通信失败 | 超时/数据格式错误/序列化 | timeout, CAN, IPC |
| 状态不一致 | 时序问题/同步缺失/竞态 | sync, race condition |
| 数据丢失 | Buffer满/消息队列溢出 | buffer full, overflow |

## 五、认知偏误警惕

### 确认偏误 (Confirmation Bias)
- **表现**：倾向于寻找支持已有观点的证据，忽略反驳证据
- **对策**：主动寻找反证

### 锚定效应 (Anchoring Effect)
- **表现**：过度依赖第一个接触到的信息
- **对策**：在深入单一线索前，先全面扫描

### 可得性启发 (Availability Heuristic)
- **表现**：认为容易想到的情况更常见
- **对策**：基于证据而非经验做判断

### 邓宁-克鲁格效应 (Dunning-Kruger Effect)
- **表现**：能力不足时高估自己
- **对策**：建立客观的置信度评分体系

## 七、警示标志：何时需要重新分析

### 🚨 红色警报 - 立即停止

1. **因果链断裂**：A → B 之间的联系不清晰
2. **数学不吻合**：理论值和实际值差异 > 10%
3. **时间序列矛盾**："原因"发生在"结果"之后
4. **存在强反证**：有明确反驳当前假设的证据

### ⚠️ 黄色警告 - 谨慎继续

1. **证据权重低**：主要依赖次要证据
2. **单一假设**：只提出了一个假设
3. **置信度过高**：没有源码确认但给出90%置信度
4. **无数学验证**：涉及时间、数量但没有计算验证

## 八、黄金法则

在给出结论前，问自己三个问题：

```
1. 我有没有搜索所有关键性能信号？
   (Long monitor contention, Skipped frames, etc.)

2. 我的因果链是否完整？每一步都有证据吗？
   (原因 → 步骤1 → 步骤2 → 结果)

3. 我做数学验证了吗？数字是否精确吻合？
   (2.746s × 60fps = 162帧 ✓)

如果任何一个答案是"否"，不要给出结论！
```

## 九、核心教训

1. **不要相信第一印象** - 表面现象往往不是根因
2. **证据为王** - 所有结论必须有强证据支持
3. **数学是最好的朋友** - 数学验证是最强的证据
4. **系统胜过经验** - 依赖系统化方法而非经验直觉
5. **多假设思维** - 永远提出多个假设，避免单一路径依赖

---

**一句话总结**：

**"用系统化的方法收集证据，用数学验证建立因果，用多假设思维避免偏见。不知道就说不知道，绝对不要胡诌！"**

<a id="ladder"></a>
## 取数的四个档位

按顺序试，命中即停。**滚动抓表是兜底手段，不是默认手段。**

| 档 | 手段 | 什么时候 |
|---|---|---|
| **0** | **先问这份数据能不能不用抓** | 见下 |
| 1 | `network` | 页面的数据来自 JSON 接口——绝大多数现代后台都是 |
| 2 | 站点的导出按钮 | 报表页往往本来就有一个点一下给 CSV 的按钮 |
| 3 | `extract` | 长文正文、文章、帖子 |
| 4 | `eval` / 滚动抓表 | 前面都不成立时的定点提取 |

### 第 0 档：先问这份数据能不能不用抓

**在写第一行抓取代码之前花十分钟问三个问题。** 任何一个是「能」，
整个抓取工程就不需要存在了——而它一旦存在，就要长期维护、会随改版坏掉、
还要在每次站点变动时重修。

1. **有没有「定时报表邮件」/「计划任务导出」？** 很多 SaaS 的导出 API 收费，
   但邮件订阅是标配功能，而且给的是完整数据。收到邮件解析附件，比抓页面稳一个数量级。
2. **换个人问一次客服。** 「API 要企业版」和「能不能给我开一个只读导出」
   是两个不同的问题，一线客服常常只回答了前一个。
3. **这个数据在别处有没有第二来源？** 同一份数字有时在另一个页面、
   另一个产品线、或某个公开端点上以更规整的形式存在。

问完再开工。**如果最后还是要抓，把这三个问题的答案记下来**——
下次别人接手时不用再问一遍，也不会以为「当初没想过」。

<a id="network"></a>
## network：接口几乎总比 DOM 可靠

```bash
opencli browser "$S" network                          # 形状预览 + 缓存 key 列表
opencli browser "$S" network --filter "title,score"   # 只保留 body 形状同时含这些路径段的条目
opencli browser "$S" network --detail <key>           # 取某一条的完整 body
opencli browser "$S" network --all                    # 包含静态资源（通常是噪音）
opencli browser "$S" network --raw                    # 全部 body 内联——很大，慎用
opencli browser "$S" network --ttl <ms>               # 缓存 TTL，默认 24h
```

列表条目形如 `{key, method, status, url, ct, size, shape, body_truncated?}`。
缓存在 `~/.opencli/cache/browser-network/`，**可以反复取而不用重新触发请求**。

> **缓存按 `key` 命中，而 `key` 可能不含你以为的那个变量**（2026-08-24 实测事故）。
> 某站所有分类的数据都走同一个 RPC 端点，于是**每个分类的 key 都相同**：
> 换了分类再 `--detail`，24h 内拿回的是**上一个分类的 body**——字段齐全、格式正确、
> 不报任何错，看起来完全像成功了。当时据此写下的「命中率很高」结论，
> 加上 `--ttl 1` 复跑后全部变回 `NO CAPTURE`。
> **凡是同一个端点带参数区分内容的场景，`--detail` 必须带 `--ttl 1`**，
> 或者每轮换一个会话。

默认输出保留 JSON/XML/纯文本和类 API 的 JS 响应，丢掉明显的静态资源和埋点。
**预期中的接口没出现时，先跑一次 `network --all`**，看是不是被不常见的
content-type 或 URL 过滤挡掉了。

`--filter` 是**路径段的 AND 语义**，不是正则：`--filter "title,score"` 保留 body 形状里
同时含 `title` 和 `score`（任意深度）的条目。

**典型流程**：开页面 → 触发那个动作（点一下按钮/翻页）→ `network --filter` 收窄 →
`network --detail <key>` 取 body。

<a id="extract"></a>
## extract：长文分块

```bash
opencli browser "$S" extract --chunk-size 8000
# -> {url, title, selector, total_chars, chunk_size, start, end, next_start_char, content}
opencli browser "$S" extract --start 8000 --chunk-size 8000
# ... 循环到 next_start_char 为 null
```

不传 `--selector` 时自动收敛到 `<main>` / `<article>` / `<body>`。

**已知的坑**：某些后台页面里会把 base64 内嵌图片一起吐出来——实测有一次
127 万字符。先用 `--selector` 圈住正文区域，或者改用 `network`。

一次性读任意公开页面还有 `opencli web read --url <url>`，
它默认展开相关的同源 iframe，对老式 iframe 外壳站点比只读顶层文档好。
AJAX 外壳页用 `--wait-for "<selector>" --wait-until networkidle --diagnose`。

<a id="eval"></a>
## eval：定点提取

```bash
opencli browser "$S" eval '(() => JSON.stringify([...document.querySelectorAll("tr")].map(r => r.innerText)))()'
```

三条硬规则：

1. **一律包 IIFE。** 本环境 eval 上下文跨调用持续，重复声明会抛错，
   **而且那次调用根本没执行**——看起来像页面有问题，其实是上一次的变量还在。
2. **`eval` 是只读的。** 要改页面就用 `click`/`type`/`select`/`keys`，
   它们有结构化输出和指纹，`eval` 没有。
3. 返回值是字符串时 stdout 就是原始字符串，否则是 JSON。

跨源 iframe 用 `--frame N`（索引来自 `frames`）。

<a id="httponly"></a>
## 脚本没有登录态而浏览器有：把请求发进浏览器

httpOnly 会话**故意**不让 JS 读到，OpenCLI 也没有导出 cookie 的命令。
遇到这种情况，正确解法不是想办法把凭据抠出来，而是**把调用挪到已登录的页面里执行**——
浏览器自动带会话，凭据全程不离开浏览器，不写 `.env`、不进日志、不进 git。

```bash
S="panel-query"
opencli browser "$S" open "https://panel.example.com/"
opencli browser "$S" eval '(async () => {
  const r = await fetch("/api/report?range=90d", { credentials: "include" });
  return JSON.stringify(await r.json());
})()'
```

这个模式同时解决了「接口需要 CSRF token」的情况——token 通常挂在页面 runtime、
meta 标签或 localStorage 里，在页面上下文里读得到。

<a id="export"></a>
## 抓表之前先找那个免费导出按钮

抓一页表要几十次滚动、要防节流、要拼行，而很多后台本来就有一个点一下给 CSV 的按钮。
开抓之前先花一分钟找它。

**四个反复踩到的坑：**

- **同名控件陷阱。** 同一个报表上常并排放着两个名字高度相似的导出控件，
  一个走付费配额、一个免费导当前页，行为完全相反。只试了其中一个就写下
  「导出被锁，只能抓取」，会把后续所有人带进沟里，而且这条错误结论会被写进文档长期生效。
  **判据：凡是要写下「某功能不可用」，先确认你点的不是同名的另一个控件。**
- **免费导出常常是静默下载**——点完页面上没有任何视觉反馈。
  不要因为「看起来没反应」就判定失败，去下载目录确认。
- **同一个工具里，不同报表的导出模型可以完全不同。** 在 A 报表上验证出
  「整包导出被锁、只能一页页导」，不构成 B 报表的结论——B 很可能一次就把几千行全给你。
  **每换一个报表，重新看一眼导出面板。**
- **一个页面上可能有多个长得一样的导出图标。** 见过的形态：报表标题栏一个
  「导出成 PDF」、表格卡片上一个数据导出，两者挂着**同一个属性值**，
  按属性 `querySelector` 会稳定取到 PDF 那个，表现为弹出 PDF 设置弹窗然后等不到
  CSV 按钮而超时。**按文案排除，不要靠出现顺序。**

**导出触发器常常是 `<svg>` 图标而不是按钮。** SVG 元素没有 `.click()` 方法，
直接调会报 `x.click is not a function`；要 `closest('button,[role=button],a')` 往上找真正的按钮。
这类面板是异步挂载的，实测要两三秒——**按坐标点会在这里稳定失联，
必须轮询等目标按钮出现再点**，不要用固定 sleep。

分页导出还有两个反复出现的形态：

- **分页多半是 URL 驱动的**（点下一页后 URL 多出 `page=N`）。确认之后就可以直接拼 URL，
  不必依赖点击。
- **翻页后表格会短暂重挂载，导出按钮会消失几百毫秒。** 等待条件必须是
  「**按钮回来了**」而不只是「数据变了」——只等后者会稳定地在第 2 页失败。

<a id="landing"></a>
## 落盘 SOP

**从浏览器、后台或第三方工具导出的任何数据文件，绝不允许留在浏览器默认下载目录。**

这不是整洁问题。默认下载目录是所有下载共用的垃圾场：文件会被随手清空、
会被同名下载覆盖成 `xxx (1)`、跨轮次跨项目混在一起无法区分，
而这些文件往往是**扣了额度或花了几十分钟才拿到、且无法凭记忆重建**的一次性产物。

**更硬的理由**：浏览器默认下载目录在部分系统上受隐私保护，终端与脚本可能
**根本读不到**（实测 shell 与 Node 同时 `EPERM`），而这种权限状态**可能在任务中途才生效**。
届时所有已下载的数据都拿不回来。[本地接收端](#receiver)方案不依赖那个目录，
因此不会中途失效——这是它排在下载法前面的原因。

如果确实只能走下载目录，落盘必须由**项目侧的一个脚本**在抓取结束后立刻完成，
而不是靠事后想起来手工搬：

1. **落到项目里。** 原始导出物与派生产物分开放（`data/<主题>/raw/`、`data/<主题>/out/`）。
2. **抓完立刻搬，不允许攒。** 每一轮抓取结束就跑落盘脚本，中间不插入别的抓取。
   攒到最后搬的后果是无法分辨哪个文件属于哪一轮。
3. **搬走而非复制。** 源文件必须从下载目录删除——留一份在那里，问题就还在。
4. **规范文件名**，自带足以区分轮次的信息：
   `<主题>__<类型>__<切片/参数>__<日期>.<扩展名>`。用参数拼名字，不要用「导出(3)」。
5. **等齐再搬。** Blob/异步下载的最后一个文件常晚几秒落盘，提前搬会**静默丢文件**
   而下游报告看起来完全正常。判据是「文件数达标 **且** 连续两次采样各文件大小不变」。
6. **归并重名副本。** 浏览器对同名下载不覆盖，而是另存为 `xxx (1)`、`xxx (2)`，
   甚至丢掉扩展名，**且这些副本内容可能不同**（重试过的目标必然产生多份）。
   同一逻辑切片只保留数据行最多的那份，其余删除。
7. **落盘即校验并记 manifest**：每个文件的数据行数、字节数、落盘日期写进同目录的
   `manifest.json`。**行数为 0 的文件必须报错退出**——空文件是抓取失败的信号，
   静默通过会让最终报告缺一整块而无人察觉。
8. **脚本参数化**：主题、类型、期望文件数、超时都从命令行传，不写死。

## 本地接收端

页面 JS 没有文件系统，`<a download>` 只能落到浏览器默认目录——这一步无法从页面内改道。
但可以**绕开整条下载链路**：在本机起一个只监听 `127.0.0.1` 的接收服务，
让页面把数据 `fetch(..., {method:'POST'})` 过去，服务端直接写进项目目录。

它一次性消掉四个问题：不需要等文件落齐、不需要归并重名副本、不受下载目录权限影响、
也不占用对话上下文。实测被采集页面的 CSP 通常不拦截到 `127.0.0.1` 的请求——
先用一个 `/ping` 端点验证连通再开跑。

**本 Skill 自带一个可直接用的实现**，不用每次重写：

```bash
node <opencli-skill-dir>/scripts/receiver.mjs \
  --root . --out data/<主题>/raw \
  --script table-extractor=/abs/path/to/extractor.js
```

端点：`GET /ping`（回报它服务的 root，**注入前先核对是不是本项目**）、
`POST /rows?slice=...`（追加一批行，回报累计数）、
`GET /script?name=...`（白名单内的提取器源码）、`POST /done`。
也可以 `import { startReceiver } from '.../receiver.mjs'` 在自己的脚本里起。

它已经做好的事：只绑 `127.0.0.1`；开 CORS（页面在 https 源上，属于跨源）；
slice 名白名单字符校验防目录穿越；端口按项目根 SHA1 派生到 41000–41900；
**占用时直接崩并打印 `lsof` 占用者，绝不静默换端口**；实际端口写进
`<out>/.receiver.json` 供其它脚本读。

### `/script` 端点解决的是「注入成本」

`GET /script?name=<白名单名>` 把本机的提取器源码喂给页面，
页面一行 `fetch(...).then(eval)` 就注入完成。

这不是锦上添花：注入提取器的唯一通道本来是把整份脚本当字符串塞进 `eval`，
而那会把脚本全文灌进对话上下文——于是每次都有人为了省这点开销**现写一个精简版**，
也就是重造轮子。加上这个端点，注入成本归零，重造的动机也就没有了。
只允许白名单里的绝对路径，不接受调用方传路径。

### 端口不能写死

**理由和会话名不能写死完全同构。** 端口是**跨任务共享的本机资源**：
两个项目同时开工时，第二个实例 `EADDRINUSE` 起不来，而后台常驻的常见写法会把输出
丢进 `/dev/null`，于是**这个失败是完全静默的**。随后页面的 `fetch` 照样返回 200——
打到的是**另一个项目的接收端**，数据写进别人的目录，`/script` 取到别人的脚本，全程零报错。

三条一起做，缺一条都堵不住（`scripts/receiver.mjs` 三条都做了）：

1. **默认端口按项目根路径派生**（哈希到一个固定区间），显式 `--port` 只在需要固定值时传。
2. **占用时崩掉并说清占用者是谁**，绝不静默退让到别的端口或复用现有实例。
   监听失败要打印排查命令，不要只抛一个 `EADDRINUSE`。
3. **`/ping` 回报自己服务的根目录**，实际端口写进项目内一个小文件，
   页面侧和其它脚本**读那个文件**而不是硬编码。注入前先核对 `/ping` 的 root 是不是本项目。

自己另写一个之前先问：这三条你都会做吗？漏掉第 2 条的后果不是崩溃，
是数据静默写进别人的目录。

**通用判据**：这个名字/端口如果被另一个任务同时用上，我会不会拿到它的数据却看不出异常？
答案是「会」，就必须按项目派生并加核对。同一条原则适用于固定端口、固定临时文件名、
固定锁文件和浏览器会话名。
